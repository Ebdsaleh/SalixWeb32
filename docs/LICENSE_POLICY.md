# License Policy

SalixWeb32 is currently developed under a restrictive source-available license rather than an open-source license.

## Current license

The repository uses:

```text
Salix Development Source License 1.0
```

The authoritative legal text is the root `LICENSE` file.

The development license is intentionally narrow. Public access to the repository is intended to support inspection, review, testing discussion, architectural study, security review, and project transparency without granting general permission to run, reuse, modify, redistribute, deploy, or incorporate the software into other projects.

Additional rights may be granted by the project owner through prior express written permission.

## Repository-hosting rights

A public repository is still subject to the repository hosting service's own terms. The development license therefore does not attempt to revoke rights that the hosting service necessarily grants to users through its normal public-repository functionality, such as viewing or forking where those platform terms require it.

Those platform rights are not intended to become a broader software-use license.

## Version policy

The development-license period is intended to cover SalixWeb32 releases through and including:

```text
v1.2.0
```

It also covers untagged development snapshots that are published under the same `LICENSE` file.

The project owner intends to publish a later release under a different and more permissive license. This is a statement of direction, not an automatic license conversion. The future license will be chosen and published explicitly when the project reaches that stage.

A later license change does not retroactively alter the terms under which earlier releases were distributed unless the project owner explicitly says otherwise.

## Contributions during the development-license period

To preserve the ability to relicense the project cleanly later, outside copyrightable contributions are not accepted by default during the restrictive development-license period.

The following remain welcome without a code contribution agreement:

- bug reports,
- build and compatibility results,
- reproducible test cases,
- feature suggestions,
- design discussion,
- documentation feedback that does not itself constitute a submitted patch for inclusion.

Code, documentation patches, assets, or other copyrightable material may be accepted only when the project owner has separately approved the contribution and any required contribution/relicensing terms in writing.

## Why the project does not use the term "clean-room license"

The project may informally describe its development policy as closed/restricted while source is visible, but the legal license is not called a "clean-room" license. In software engineering and intellectual-property practice, clean-room development usually refers to independently reimplementing a system without access to protected implementation details. That is a different concept from the source-available restrictions used here.

## Future license selection

The post-v1.2.0 license has intentionally not been selected yet. The choice should be made when the project's long-term distribution, contribution, plugin, embedding, and commercial-use goals are clearer.

Possible future directions may include a permissive license, a copyleft license, a weak-copyleft license, or a dual-licensing model. None of those options is promised by the current development license.
